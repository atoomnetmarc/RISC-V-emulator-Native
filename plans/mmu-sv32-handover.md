# Handover: Sv32 MMU, ACT generation

## Context

The Sv32 MMU plan is `plans/mmu-sv32.md`. M1 (S-mode privilege and trap plumbing) and M2 (Sv32 translation) are code-complete. The work is making the three Sv32 ACT configs generate and build.

## What is done

- The ISA-combination generator emits three Sv32 environments:
  - `RV32IZicntr_Zicsr_Sv32` / `rv32izicntr_zicsr_sv32` (minimal)
  - `RV32IMAZicntr_Zicsr_Zifencei_Sv32` / `rv32imazicntr_zicsr_zifencei_sv32` (Linux set)
  - `RV32IMACBZicntr_Zicsr_Zifencei_Sv32` / `rv32imacbzicntr_zicsr_zifencei_sv32` (maximal set)
- Each env enables `RVE_E_ZICNTR=1`.
- `scripts/gen_core.py` emits `STANDARD_SM_SUPPORTED`, the CLINT timer addresses and `include_priv_tests` for the Sv32 subset.
- `config/cores/template/sail.json` delegates every standard exception, including bit 0.
- The three configs regenerate and all three PlatformIO envs build.
- The tools container applies two temporary ACT 4.1.0 source patches, documented in `PATCHES.md`:
  - `patches/trap-sigupd-count-zaamo-umode.patch` raises `TRAP_SIGUPD_COUNT` in `tests/priv/ExceptionsSvZaamo/sv32_exceptions_Zaamo_Umode.S` from 110 to 270.
  - `patches/identity-map-ahead-of-smode.patch` places the `rvtest_identity_map` block directly after `RVTEST_BOOT_TO_MMODE` in `tests/env/rvtest_setup.h`, ahead of the `RVTEST_BOOT_TO_SMODE` call.
- `config/cores/template/sail.json` sets `pmp.count` and `usable_count` to 0. The three configs are regenerated with `scripts/gen_core.py`.

## The identity-map finding

The S-mode prolog enables `satp` with an empty root page table. The identity-map PTE is written by code that runs in S-mode. The first S-mode fetch faults on the empty table, and the S-mode handler faults in the same unmapped region. The patch writes the PTE in M-mode, where `satp` has no effect. The trap loop moves from `0x800356b4` to `0x8003572c`.

## The PMP finding

The generated sail config has `pmp.count: 16` and `usable_count: 16`, but the test has `UDB_NUM_PMP_ENTRIES 0` and programs no PMP entry. The sail model denies every S-mode fetch with `PMP check failed with no matching entry`. The template sets PMP to 0, and the three configs are regenerated.

## Remaining failure

A direct sail run with the regenerated config reaches a T-SBI error:

```
T-SBI ERROR: requested instruction not found in tsbi_instr_table: 0xfddb7d5b
```

The value `0xfddb7d5b` is the `RVTEST_INIT_REGS` value for `a0`. The test is generated by `generators/testgen/src/testgen/priv/extensions/ExceptionsS.py`. The T-SBI handler is in `tests/env/rvtest_trap_handler.h`.

### Boot order

`rvtest_setup.h` runs, in order: `RVTEST_BOOT_TO_MMODE`, the identity map, `RVTEST_BOOT_TO_SMODE` (which executes `RVTEST_TSBI_GOTO_SMODE` with a0=2), clearing the trap counter, `RVTEST_INIT_REGS` (a0=0xfddb7d5b), and finally a jump to `rvtest_code_begin`. The boot ecall therefore carries a0=2; the init value is only live from the first instruction of the test body onward.

### Ecalls in the test body

The first ecall is `RVTEST_TSBI_ECALL_TEST` (a0=0x73). Every later ecall sets a0 through `LI(a0, encoding)` or a `RVTEST_TSBI_GOTO_*` macro. No generated ecall intentionally uses the init a0.

### Working hypothesis

`tsbi_instr_not_found` prints a0, so an ecall reaches the M-mode handler with a0 never set. The only code between `RVTEST_INIT_REGS` and the first ecall is the misaligned-fetch block, so the first `RVTEST_TSBI_ECALL_TEST` is the likely site: the `li a0, 0x73` is skipped or a0 is overwritten on the way. The suspect is the xEPC relocation path for the misaligned-fetch trap returning to the ecall instead of the `li`, not the generator.

### S-mode CSR privilege check

The S-mode handler decides "M-mode CSR, forward to M-mode" with `CSR_addr[11:10] == 3`, but the privilege level is encoded in `CSR_addr[9:8]`. For `mstatus` (0x300) `[11:10]=00`, so the handler treats it as an S/U CSR and executes it locally from scratch; that is an illegal instruction in S-mode. This produces a trap/signature problem, not directly the 0xfddb7d5b error.

### Artifacts

The generated `ExceptionsS-00.S` and the `work/.../gcc` and `elfs` outputs are absent; the work dirs contain only `state.lock`. The failing run cannot be inspected without a rerun. The `make elfs` run reports `605 up-to-date` and does not rerun the failed test. Force a rerun by removing the stamps and the `elfs`/`build` outputs, or use the framework's reset.
